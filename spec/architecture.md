Why the stack looks like this, not a tour of files. Next.js 16 here is not the Next.js in most training data — read `node_modules/next/dist/docs/` and the agent-rules block in [`CLAUDE.md`](../CLAUDE.md) (`cce733b`) before changing framework APIs. In Server Actions, immediate cache invalidation uses `updateTag(tag)` (`#144`), while `revalidateTag` requires a profile argument (`98edc57`). ## Data: constants → Drizzle → gold upserts

**Dec 2025.** League data lived in `app/lib/constants.ts` and static TS modules. Fast to ship; every score change was a commit.

**Jun 2026 (`e4e53f7`).** Drizzle + Supabase Postgres (`postgres` driver). Hierarchy that stuck: **Game → Season → Team (school × game × season) → Roster (Varsity/JV) → Player (member)**. Matches reference roster IDs (`5b803f8`), because archived CSVs labeled divisions A/B and Varsity/JV need independent records. Computed `roster_standings` view replaced stored W–L on teams.

February’s `DATABASE.md` (`cf27afb`) described a different model (`people`, `team_staff`, `org_staff`, JSONB match maps). June implemented **`members` + a flat `leadership` table** instead — closer to admin UX. The aspirational doc was deleted when it became misleading (`2efca7b`). A `people` table did arrive in August, but only as **org-staff identity** (`f14c7f4`), not the February “everyone is a person” design. See [`specs/leadership-architecture.md`](../specs/leadership-architecture.md). The spec’s “fall back to legacy `leadership`” line is not implemented: `getCachedLeadership()` inner-joins `people` + `leadership_terms` only. The legacy `leadership` table remains in `schema.ts`.

**Jun 15 (`930299c`).** Dummy seed replaced by a one-shot import of two gitignored root CSVs. 389 Valorant matches landed `scheduled` with null scores. No bronze/silver/gold yet.

## Auth / RBAC

1. Supabase SSR cookies (`784f3d7`) — any signed-in user could hit `/admin`.
2. Allowlist + hashed invites (`0849963`, PR #8). Auth ≠ authorization.
3. Discord-style `roles` / `user_roles` / `staff_members` (`ad77369`, late June).
4. Granular permissions, membership vs capability split (`0019`, PR #18). Flags in `app/lib/roles.ts`: `MANAGE_ROLES`, `MANAGE_LEAGUE`, `MANAGE_ROSTERS`, `MANAGE_MATCHES`, `MANAGE_NEWS`, `MANAGE_LEADERSHIP`, `MANAGE_GALLERY`, `MANAGE_SPONSORS`, `MANAGE_APPLICATIONS`, `MANAGE_SCHOOLS`, `MANAGE_CONTENT`. Owner/`ADMINISTRATOR` bypass. Section map: `ADMIN_SECTION_PERMISSIONS` in `app/lib/staff-access.ts`; gate: `getStaffForAdminSection` in `app/lib/auth.ts`. Roster data is not a section: `ADMIN_ROSTER_VIEW_PERMISSION` (`MANAGE_ROSTERS`) gates `/admin/schools/[schoolId]/rosters` via `getStaffWithPermission` ([spec-024](spec-024-schools-roster-view.md)).
   - **Role hierarchy invariants (incidents section 18).** Higher `roles.position` = higher rank. Owner roles are always at the top; non-owners can never grant or manage an owner role regardless of position (`canManageRole` requires `targetRoleIsOwner`); new roles are created below owner roles via `nextRolePosition`, which fails instead of placing a role at or above one.
5. `staff_revocations` tombstones (`0020`). A revoked identity stays revoked across user recreate; restore is an explicit trusted workflow (`docs/QUICKSTART.md` `--restore-revoked`). `pg_advisory_xact_lock` vs self-heal race (`29465a7`).
6. **Lock-then-re-read pattern (`37515cd`, PR #181 / #156).** Role assignments (`assignStaffRole`), edits (`updateStaffRole`), and invite revocations in `app/(admin)/admin/team/actions.ts` acquire `pg_advisory_xact_lock(STAFF_REVOCATION_LOCK_KEY)` and re-read live database roles inside `tx` to eliminate TOCTOU privilege races.

**No advisor RBAC preset.** Bitmask can express applications-only; there is no school-advisor scoped model.

RLS is on (`0012`+, `4be3c49`). Storage writes/deletes use the **service-role** client (`3cce264`). PR #182 (`bbae922` #152) stopped trusting client-supplied deletion keys in `admin-uploads`, enforced section permissions (`Permissions.MANAGE_*`), instituted deterministic scoped storage folders (`${section}/${entityId}/${timestamp}.${ext}` with path traversal sanitization), and made deletes server-derived. Companion cleanup script: `db/storage-clean.ts` (`npm run db:storage:clean`). The Student Handbook PDF ([spec-021](spec-021-student-handbook-page.md)) also lives in `admin-uploads` under `handbook/<timestamp>.pdf`, written by `/api/handbook` and recorded in the `page_content` row `handbook_pdf` (upserted; hidden from the text-block editor). Its key shape is validated server-side before it is stored or rendered. The public page renders that PDF client-side with `pdfjs-dist` (dynamic import in `app/lib/handbook-pdf.ts`; same-origin worker; CSP `worker-src 'self' blob:`), since framing PDFs is blocked by `frame-ancestors 'none'`.

Applicant resumes are the one **private** bucket: `staff-resumes` (`STAFF_RESUME_BUCKET`, [spec-007](spec-007-staff-application-resume.md)). The public staff-apply route writes to it with the service client only after all validation passes (including the `%PDF-` magic bytes), under a random `<uuid>.pdf` key, and stores the key in `staff_applications.resume_storage_key`, never a URL. The only read path is `GET /admin/applications/staff/[id]/resume`, which is gated by `getStaffForAdminSection('/admin/applications')` and 303-redirects to a 60 s signed URL.

Rate limit exists for apply POST, staff apply, uploads, staff invites, `/login` (PR #131) and `/portal/login`, keyed per IP and per IP+account (`app/lib/rate-limit.ts` — in-process Map, resets on serverless cold start; comment points at Upstash).

**Security headers and CSP.** Static headers (X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy, HSTS) live in `next.config.ts` (PR #129). The Content-Security-Policy is per-request and nonce-based (PR #141): `updateSession` in `app/lib/supabase/middleware.ts`, called from `proxy.ts`, builds it with `buildCsp(nonce)` and sets it on both request and response.

## Timezone Canon: America/New_York (ET)

All league competition occurs in NYC and canonicalizes to Eastern Time (`America/New_York`). PR #184 (`41270c5` #148) standardized this contract:
- `parseEastern(dateStr)` in `app/lib/dates.ts` parses local input strings (`YYYY-MM-DDTHH:MM`) into exact UTC instants on UTC servers across EDT/EST transitions, eliminating the 4-hour kickoff drift from naive `new Date()`.
- Public schedule pages and calendar grids explicitly display "ET" (`7:00 PM ET`) and calculate calendar month matrices in America/New_York using UTC date math to avoid client local timezone shifts.
- Status normalization: forfeits are treated as completed (never upcoming), draws display as `D <score>` rather than losses, and 0-0 forfeits do not hijack upcoming match focus.

## Staff match list: tabs and counts are server-side (spec-030)

`getMatchesPage` accepts a `tab` (`needs-results | upcoming | completed | all`) and a `now`; "past" is a UTC-instant comparison against the server clock, mirrored by the pure `matchTabOf` in `db/match-page.ts`. ## Caching

`unstable_cache` tags at HEAD: `games`, `schools`, `members`, `teams`, `seasons`, `matches`, `rosters`, `players`, `news`, `leadership`, `people`, `tournaments`, `sponsors`, `page-content`, `gallery-images`. `recent-results` is a cache **key** on the League Pulse query, not a tag — its tags are `matches`, `schools`, `rosters`, `teams`, `games`, `seasons`. Admin mutators call `updateTag(tag)` (PR #195). Entries live in **Vercel Data Cache** and survive redeploys. UUID-changing seeds/migrations leave pages empty against a healthy DB — that is the July 30 failure mode. After `9219ef5`, gold upserts exist specifically so row IDs stay stable. There is still no dedicated cache-purge tool.

## Manager portal guided tour

One tour definition (`app/(portal)/portal/tour/steps.ts`) targets stable `data-tour` attributes, never selectors or text; `resolveTourSteps` slices it for the full tour or one section and drops steps with no target. Dismissal is the nullable column `school_managers.tour_completed_at`: read server-side by `hasCompletedPortalTour()` (true if any of the user's rows is set; true with no rows or on error), written by `completePortalTour()` (stamps all of the user's unset rows) only when the first-run tour ends. Each person has their own rows, so another manager at the same school is unaffected. The popover is a non-modal RAC `Popover` (a modal one locks page scroll, which blocks scrolling targets into view); Esc and arrows come from a document-level listener. A test renders the portal for a school with no data and fails if a referenced anchor is missing. See [spec-015](spec-015-manager-portal-guided-tour.md).

## Match reschedule requests (spec-032)

A request never writes `matches.scheduled_at`: only `approveReschedule` does, in a transaction that also checks the match is still `scheduled` at the request's `original_scheduled_at`. Rules live in the pure `app/lib/reschedule-rules.ts` and are enforced in the server actions (`app/lib/onboarding/reschedule-actions.ts` for managers, `app/(admin)/admin/matches/reschedule-actions.ts` for staff). Every transition is a conditional update, and a partial unique index allows one open request per match. The portal and staff reads (`app/lib/db/reschedules.ts`) fail soft so a problem there cannot hide the schedule or the results page. A request has one counter round: the opponent may answer with times of their own (`pending_requester`), each time carries `proposed_by`, and a school can only pick the other side's times (a SQL condition in `respondToRescheduleImpl`, asserted in the action tests). Tables `match_reschedule_requests` and `match_reschedule_options` (migration 0053, hand-written; RLS on, no policies).

## Roster membership: sibling rule and change seam (spec-034)

Rosters of one team (one school, one game, one season) are **siblings**, and a member may be on at most one of them; across games a student can hold different tiers. The check is `siblingEnrollment` in `app/lib/db/roster-scope.ts`, enforced in application code inside the write transaction by manager `enrollPlayerToRoster`, the approve path of `reviewPlayerInvite`, staff `createPlayer` and both move actions (a move is an in-place `UPDATE players SET roster_id` guarded by `AND roster_id = <source>`). Every one of them first takes `lockRosterMember` (`pg_advisory_xact_lock` keyed on team + member) so two concurrent requests cannot both pass the check. There is no database constraint, so writers outside these actions (seed scripts, hand-run SQL) are not covered, and pre-existing violations are tolerated on the roster they are on.

**Roster size limits.** A roster holds at most 10 players and 5 subs ([spec-048](spec-048-roster-size-10-and-five-subs.md); was 7 and 2) (`MAX_ROSTER_PLAYERS`, `MAX_ROSTER_SUBS` in `app/lib/onboarding/roster-limits.ts`). The caps apply when adding (manager enroll, including placing an accepted invite, staff add, both moves: target roster counted) and when changing someone to sub; they never apply to `emergencySwapSub`. Counting happens inside the transaction under `lockRoster` (taken after `lockRosterMember`, always in that order). **`getRosterEligibility` stays minimum-only and must not reference the caps** (a test reads its source). The caps are app-level only (no database constraint; seeds and hand-run SQL bypass them) and rosters already over them are left alone. See [spec-034](spec-034-roster-move.md).

**Manager roster actions return expected rejections as `{ success: false, error }`** (`RosterActionRejection` in `portal-actions.ts`) instead of throwing, because Next.js omits thrown server-action messages in production. Unexpected errors and the authorization / lock / view-only guards still throw; the older neighbouring actions are unchanged.

**The roster-membership seam.** `notifyRosterMembershipChanged(memberIds)` (`app/lib/onboarding/roster-membership-events.ts`, a no-op today, reserved for Discord role sync) is called after the transaction commits, never inside it, and must never throw into the caller. It is called from the manager enroll / remove / move / emergency-swap / role-change / invite-approve actions and the staff add / role-change / remove / move / delete-roster actions. It is **not** called when a game or season is deleted (`app/lib/db/league.ts` relies on the database cascade and never reads who was on the rosters), by `db/seed-gold.ts` and the ingestion scripts, by manager `deleteSchoolRoster` (empty rosters only), or for member edits that do not touch rosters. A consumer must treat the call as a hint, re-derive state from the database, and reconcile periodically. See [spec-034](spec-034-roster-move.md).

## Confirm-then-act uses ConfirmActionDialog (spec-037)

Never call native `confirm()` in `app/` (ESLint `no-restricted-globals` / `no-restricted-properties`, plus a vitest scan): embedded browsers dismiss it instantly, so the control looks dead. A destructive or irreversible control opens `ConfirmActionDialog` (`tone="danger"`, Cancel focused first) driven by `useConfirmAction`; the server action runs only from the dialog's confirm, a failure is shown inside the dialog, and the confirm button is `aria-disabled` while pending. Hooks that return handlers (`useSchoolManagersData`) must not confirm; the component that owns the button renders the dialog. Use `appearance="portal"` under `/portal`, and pass `restoreFocusRef` when the trigger is a menu item. `alert()` and `prompt()` are still used in places (see open threads). See [spec-037](spec-037-in-app-confirm-dialogs.md).

## Match results from game data (spec-038)

Ports and adapters again: `app/lib/match-results/types.ts` defines `MatchDataPort` and `NormalizedGame`; `henrik-adapter.ts` (HenrikDev v4, key `VALORANTAPI`, server-only via `server.ts`) is the only provider-specific code, with `henrik-schema.ts` validating the unofficial payload with zod. `series.ts` (pure) attributes Red/Blue to the home/away roster by Riot ID and scores the best-of-3; `resolve-series.ts` takes an injected `GameRepository` so cache, duplicate and 429/outage rules are testable. Finished games are cached forever in `valorant_games` / `valorant_game_players` (unique `riot_match_id`); `match_games` attaches them to a league match (`game_id` unique = a game counts once); `match_result_submissions` holds a waiting submission (one open per match). `saveSeriesResult` writes games, `home_score`/`away_score` and `completed` in one transaction, and the action calls `updateTag('matches' | 'rosters' | 'teams')`. The raw provider payload is not stored (PII). No test or CI path calls the live API. A Riot-official adapter later replaces `henrik-adapter.ts` only.

## Manager who also plays (spec-043)

`processOnboardingSubmission` resolves the member once by email (`upsertMemberRecord`) and compares the Discord identity owner to that member id, so a manager and a player are one `members` row with one Discord `player_identities` row; the unique `(provider, provider_user_id)` index still refuses a different member. For a manager invite with `alsoPlays === true` the submitted `playGameIds` are validated against `games` (`findExistingGames`, rejection `play_games_required`) and, inside the same transaction, `ensurePlayerSubmission` inserts one `submitted` `player_invites` row per game (random unreachable `token_hash`, `submission_draft.source = "manager_also_plays"`), skipping games the member already has a live row for. Approval is the ordinary `reviewPlayerInvite`, so season scope, roster lock and sibling/size rules apply unchanged. `sanitizeGameIds` lives in `play-games.ts` because `wizard-actions.ts` is a `use server` file and may only export async functions. See [spec-043](spec-043-manager-also-plays.md).

## Onboarding content screen and fail-safe DB access (spec-040)

`app/lib/profanity/` (`terms.ts` data, `detect.ts` rules) is pure and dependency-free; `app/lib/onboarding/content-check.ts` says which onboarding fields are screened and is imported by both the wizard (`useWizardDraft`, `ContentFlagNotice`) and `processOnboardingSubmission`, which recomputes the flags server-side and rejects `content_flagged` unless the field is in `contentOverrides`. Overrides are stored in `onboarding_content_flags` (migration 0055), deliberately a separate table and never a column on `members`/`players`, and read in a separate query from the roster read. **Pattern for any code that may deploy before its migration:** wrap every statement in a helper that treats only Postgres `42P01`/`42703` naming that table (also through Drizzle's `.cause`) as "not migrated", logs a warning and degrades; write inside a savepoint (`tx.transaction`) when it runs in a larger transaction so a failed statement does not abort it. See `app/lib/db/content-flags.ts` (compare `thumbnail-columns.ts`). See [spec-040](spec-040-onboarding-offensive-content-screen.md).

## Second-tab Discord verification and the cross-tab channel (spec-041)

`PlayerOnboardingWizard` opens `/api/discord/start?...&popup=1` in a second tab so it never unmounts (a manager's password and the content-screen overrides stay in memory). `popup` rides in the signed flow cookie and the callback redirect; the join page renders `DiscordPopupDone` for `popup=1`. That tab broadcasts `{ inviteId, status, error? }` through `app/lib/onboarding/discord-channel.ts` (BroadcastChannel, `storage`-event fallback; both guarded). The message is a wake-up only: the wizard then calls the server action `getVerifiedDiscordForInvite(token)` (`wizard-actions.ts`, reads the signed result cookie through `readVerifiedDiscord`, returns `{ username, inGuild } | null`), so identity still comes only from the signed httpOnly cookie. Fallbacks: blocked/closed pop-up falls back to the same-tab redirect; focus and a 5 s poll re-check the cookie; a closed tab ends the wait; Cancel and a ten-minute cap end it. See [spec-041](spec-041-discord-oauth-second-tab.md).

## Season generation: pure scheduler, preview/commit with a lock (spec-046)

`app/lib/season-schedule.ts` (circle-method rounds, 7-regular for even n >= 8, kickoffs at 7 PM ET via `parseEastern`) and `season-generation.ts` (what to create) are pure. `generate-season-actions.ts` previews without writing; commit runs in one transaction that locks the season row, rechecks "no matches yet", and verifies the preview fingerprint. ## Manager portal season scope
School managers are scoped by season, not just school and game (spec-019). Season names and `school_managers.academic_year` are both `YYYY-YY` (`app/lib/season-name.ts`), so a manager's season for a game is the game's season whose name equals the `academic_year` of one of their rows covering the game, active or not; several matches resolve to the newest name, and no match means nothing for that game ([spec-026](spec-026-manager-season-by-name.md), superseding spec-019's active-season-only rule). The checks live in `app/lib/onboarding/manager-auth.ts` (`resolveManagerSeason`, `assertManagerForSchool` / `assertManagerForSchoolGame`, `assertManagerForRoster`, `getAuthorizedGameScopes`) and `portal-actions.ts` reads filter through the resulting scopes. A staff admin means the ADMINISTRATOR permission, checked before manager rows; a `staff_members` row alone never grants the all-season view. **Inactive seasons are view-only for managers ([spec-028](spec-028-manager-past-season-view-only.md)):** the rule is just `season.isActive === false` (older or newer than the game's active season alike; no name comparison). `assertManagerForSchool` / `assertManagerForSchoolGame` / `assertManagerForRoster` refuse writes on it by default through `assertSeasonActive` (reads pass `allowInactive: true`), and scopes expose `readOnly` / `readOnlyReason` next to `seasonIsActive`. There is a single portal write path: the former unused hexagonal `PortalService` (a drift-prone parallel copy of these rules) was deleted on 22 Oct 2026 ([spec-028](spec-028-manager-past-season-view-only.md)); `DrizzleOnboardingRepository` remains only for staff manager provisioning and the candidate wizard services.

**Season outcome gate (spec-022).** `seasons.outcomes_finalized_at` (null = hidden) is read through `areOutcomesPublic` (`app/lib/season-outcomes.ts`); public data functions (`getSeasonStandingsFor`, `getGameSeasonSummary`, `getTeamStandingsRecords`, `getPublicMatchesPage`, `getPublicSeasonMatches`, `getCachedRecentResults`, `getArchiveIndex`) redact before returning. As of spec-049 the same flag also removes an unpublished season's matches from public reads entirely (`getPublicMatchesPage` filters in SQL via `getMatchesPage(params, true)`; `getPublicSeasonMatches` returns `[]`; hub `nextMatch` and archive `matchCount` are empty). Staff reads stay raw. Publishing refreshes the `seasons`, `matches`, `teams`, `rosters` tags and the public routes.

**Season roster lock (spec-020).** `seasons.rosters_locked_at` (null = unlocked) freezes a season's rosters for school managers (applied to the manager's resolved season, active or not, per spec-026). The check lives in `manager-auth.ts`: `assertManagerForRoster` refuses a locked season by default (reads pass `{ allowLocked: true }`), `createSchoolRoster` and the default-roster branch of `reviewPlayerInvite` call `assertSeasonRostersUnlocked`, and staff admins are exempt. Staff toggle it with `lockSeasonRosters` / `unlockSeasonRosters` (MANAGE_LEAGUE). The portal reads the column uncached, so a toggle applies on the next request; the actions still `updateTag('seasons')`.

## Roster removal and orphan cleanup (spec-042)

`app/lib/db/roster-removal.ts` is the only place a roster spot is removed together with the student's own record. `removePlayerFromRosterTx(tx, ...)` deletes the `players` row, then `cleanupOrphanMember` locks the member (`FOR UPDATE`), checks the keep-reasons (other roster, staff, school manager or manager invite, leadership/people profile, gold-archive `member_key`, match-history evidence) and otherwise deletes consents, demographics, identities, player invites and the member. The cleanup runs in a savepoint: unexpected errors keep the member and still commit the roster removal; 42P01/42703 on an optional table counts as "no rows" (no migration needed). Nothing references `players.id`; history is inferred (see the spec). Callers keep their own permission, school scope, cache tags (`members` joins `rosters`/`players` only when a member was deleted) and the post-commit `notifyRosterMembershipChanged`.
