# spec-063: Staff-issued one-time password reset links

- **Status:** Implemented on branch `worktree-agent-ab14843f5de9b677e` (unmerged). **Migration `0062` is written but NOT applied to production.**
- **Date:** 2026-11-13
- **Scope:** table `password_reset_links`, the pure service in `app/lib/password-reset/`, three staff server actions, the public `/reset-password` page, a dialog on the Staff team rows and the School Managers dialog.

## Problem

A school manager forgot their portal password. There is no outbound email (free-tier limits), so a standard Supabase reset is unavailable. Staff already reach managers over Discord tickets. Staff need to hand over a one-time link that lets the person set a new password on the **same** Supabase Auth account, so roster links and history are kept.

## Decisions

- **Who can issue.** Manager accounts: `MANAGE_SCHOOLS`, the gate on every manager-invite action (`app/(admin)/admin/schools/manager-actions.ts`, `requireSchoolsPermission`; spec-011 names the same flag). Staff accounts: `MANAGE_ROLES`, the gate on `inviteStaff`, `revokeStaff` and `updateUserRoles` and on `/admin/team`. The owner and `ADMINISTRATOR` bypass in `hasPermission` applies as everywhere. The kind comes from the client, so the actions use `requireStaff()` and `checkKindPermission` picks the permission per kind (`permissionForKind`).
- **Escalation guard (interpretation).** `revokeStaff` and `updateUserRoles` guard with `canActOnMember`: an Owner may act on anyone; otherwise the target must not be an Owner and the actor's highest role position must be **strictly greater** than the target's. The same function runs here whenever the target has a `staff_members` row, **for either kind**: a `MANAGE_SCHOOLS` user must not be able to reset an Owner or a higher-ranked staff account just because that person also has a manager row. Consequences: an equal-rank non-owner cannot reset a peer; an Owner account is only resettable by an Owner; a plain manager (no staff row) is limited only by `MANAGE_SCHOOLS`. A staff member cannot issue a link for their own account (even an Owner). Revoking an outstanding link applies the same hierarchy check, but a deactivated target no longer blocks revoking its old link.
- **Deactivated accounts (interpretation).** "Deactivated" means: manager kind = no `school_managers` row with `is_active = true` for the user; staff kind = no `staff_members` row (revocation deletes it and writes a tombstone). Issuing is refused for these, and redeeming re-checks eligibility so a link issued earlier dies with the account (generic message). A Supabase-level ban (`banned_until`) is not checked.
- **Token.** `generateInviteToken()` (256-bit `randomBytes`, hex) and SHA-256 `hashInviteToken`, the same helpers as `manager_invites` and staff invites. Only the hash is stored. The raw token is returned once by `issuePasswordResetLink` as a path (`/reset-password?token=...`), held only in the dialog's React state, never persisted or logged (the action's error logging prints the message only).
- **Lifetime and lifecycle.** 24 hours (`RESET_LINK_TTL_MS`), single use. A partial unique index `password_reset_links_one_outstanding_idx` (`user_id` where `used_at is null and revoked_at is null`) allows at most one outstanding link per user; issuing revokes the previous one (`revoked_by` = the issuer) and inserts the new one in one transaction. Staff can revoke an outstanding link. Status is derived: used, then revoked, then expired, else outstanding (`resetLinkStatus`).
- **Redeem order.** (1) look up the hash, require outstanding and an eligible account; (2) check the password rules; (3) **claim** the link atomically (`update ... set used_at where used_at is null and revoked_at is null and expires_at > now returning`), so two concurrent submissions cannot both pass; (4) `auth.admin.updateUserById(userId, { password })`; if that fails the claim is released and the link stays usable, and the old password was never touched; (5) end all of the user's sessions; (6) redirect. The old password therefore stays valid until the new one is set. A failed claim release (unique-index conflict because staff issued a newer link in between) is swallowed: the link stays spent and staff issue another.
- **Session revocation.** `supabase.auth.admin.signOut(jwt, scope)` needs the user's own JWT, which a staff-issued reset never has. The adapter instead runs `delete from auth.sessions where user_id = $1` through the existing service-role database connection; refresh tokens cascade, which is what a global sign-out does. Already-issued access tokens stay valid until their normal expiry (they can no longer be refreshed). If this delete fails after the password changed, the failure is logged (`onSessionRevocationFailed`) and the reset still succeeds (the link is spent; failing would strand the user); staff can see it in the logs. Not verified against a live Supabase project (see open threads).
- **No auto sign-in.** The public action never creates a session. On success it redirects to the matching login page with `?message=password-reset` (managers: `/portal/login`, staff: `/login`, from the link's `target_kind`).
- **Public page `/reset-password?token=...`.** Top-level route like `/accept-invite` (`force-dynamic`, noindex, `referrer: no-referrer`). Server component calls `peek()` and shows either the form or one generic message. Invalid, expired, used, revoked, unknown and deactivated all render `INVALID_RESET_LINK_MESSAGE`, in the page and in the action; the page does not show the account's email. Password rules are the sign-up/onboarding rules: minimum 8 characters (`MIN_PASSWORD_LENGTH` in accept-invite, `MANAGER_PASSWORD_MIN_LENGTH` in onboarding), plus a confirmation field. Supabase's own password policy still applies and a rejection is shown as a retryable error without burning the link.
- **Abuse protection.** The repo's only limiter is the in-process sliding window in `app/lib/rate-limit.ts` (resets on cold start, per instance). The page and the action share a per-IP bucket (20 per 15 minutes), and issuing is limited to 20 per minute per staff member. This is a best-effort brake; the real protection is the 256-bit token, which cannot be guessed, plus the 24 hour life. No new infrastructure was added.
- **Audit table `password_reset_links`.** `id`, `user_id` (Supabase auth id, no FK), `target_kind` ('manager' | 'staff', CHECK), `token_hash` unique, `issued_by_user_id`, `created_at`, `expires_at`, `used_at`, `revoked_at`, `revoked_by`. RLS enabled with no policies, like `player_invites` and `manager_invites`; the app uses the service role. Nothing about the user's email or the raw token is stored.
- **Admin UI.** One `PasswordResetDialog` (`app/components/admin/PasswordResetDialog.tsx`, built on the `Overlay`/`Modal`/`Dialog` wrappers, no `confirm()`): Generate button, the link in a read-only field with a Copy button shown once, the 10 most recent links with a status chip (Outstanding / Used / Expired / Revoked), who issued each and when, and Revoke on the outstanding one. Opened from a key icon on each row of the School Managers dialog's Active tab and from a "Password reset link" item in each staff row's actions menu (shown only when `canRevoke` and not self). Revoke has no confirm step (cheap and reversible by issuing a new link).
- **Cache.** No `unstable_cache` tag is read or written by these actions, so there is no `updateTag` call. History is read live through `listPasswordResetLinks`.
- **Hardening done on the way.** `/portal/login` printed `?message=` verbatim; it now maps through the same allowlist as `/login` (`MESSAGE_MAP`, new key `password-reset`).
