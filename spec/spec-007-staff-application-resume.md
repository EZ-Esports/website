# spec-007: Staff Application Resume Upload, Volunteer Acknowledgement, and Recruiting Intro

- **Status:** In Progress (code on `fix/staff-apply-tidy`, not deployed; migration `0036` and the `staff-resumes` bucket are **live in production** as of 2026-09-26)
- **PR:** not opened yet
- **Date:** 2026-09-25 (follow-up round 2026-09-26)
- **Scope:** `app/(marketing)/apply/staff/StaffApplyForm.tsx`, `app/(marketing)/privacy/page.tsx`, `app/api/apply/staff/route.ts`, `app/lib/staff-application-form.ts`, `app/lib/staff-resume.ts` (new), `app/(admin)/admin/applications/staff/[id]/resume/route.ts` (new), `app/components/admin/StaffApplicationDetailModal.tsx`, `app/components/admin/StaffApplicationRow.tsx`, `app/lib/application-csv.ts`, `app/lib/db/queries.ts`, `app/lib/db/schema.ts`, `db/migrations/0036_staff_application_resume.sql`, tests under `app/lib/__tests__/` and `app/lib/db/__tests__/`.

## Context & Motivation

`/apply/staff` had a single optional "LinkedIn profile or Portfolio/Resume link" text field, so reviewers often had no resume at all. The recruiting message also needed to state up front that roles are unpaid, part-time volunteering, and the page intro needed the organization's recruiting copy (from a Discord recruiting post) and the mission statement.

The form is public and unauthenticated, and a resume is PII (name, contact details, school history). It cannot go in the public `admin-uploads` bucket used for site imagery.

## Design Decisions

1. **Resume: required PDF in a private bucket.**
   - Bucket `staff-resumes` (constant `STAFF_RESUME_BUCKET` in `app/lib/staff-resume.ts`), **private**. Created by hand in the Supabase dashboard, not from code or a migration: private, 5 MB bucket file-size limit, allowed MIME type `application/pdf`.
   - The route handler caps a resume at **4 MB** (`RESUME_MAX_BYTES`), below the bucket's 5 MB, because the whole multipart request must fit under Vercel's 4.5 MB serverless request-body limit. A body whose declared `Content-Length` exceeds 4 MB + 256 KB gets a 413 before it is parsed.
   - Server validation (`validateResumeUpload`): present, `.pdf` name or `application/pdf` type, non-empty, at most 4 MB by actual byte count, and the bytes start with `%PDF-`. The magic-byte check is authoritative; type and extension are client-controlled.
   - Storage key is `<randomUUID>.pdf`: nothing about the applicant is in the key. The key goes in the new `staff_applications.resume_storage_key` column. No URL is stored.
   - Order in `POST /api/apply/staff`: rate limit (unchanged, 5 per IP per 10 min), body-size check, field validation, `details` validation, resume validation, **then** upload, then insert. A rejected request never writes to storage. If the insert fails after upload, the route removes the object.
   - The submission changed from JSON to `multipart/form-data`: the applicant fields, `details` as a JSON string, and `resume` as a file part.

2. **Admin access by short-lived signed URL.** `GET /admin/applications/staff/[id]/resume` checks `getStaffForAdminSection('/admin/applications')` (the same gate as the Applications page, i.e. `MANAGE_APPLICATIONS`), rejects a malformed id, looks up the key on a non-deleted row (`getStaffResumeStorageKey` / `buildStaffResumeKeyQuery` in `queries.ts`, whose `deleted_at IS NULL` filter is asserted on the generated SQL), and 303-redirects to a Supabase signed URL valid for **60 s** (`RESUME_SIGNED_URL_TTL_SECONDS`), with `Cache-Control: private, no-store`. The detail modal renders a plain "View resume (PDF)" link to this route. The applications query exposes only `hasResume` (`resume_storage_key IS NOT NULL`), never the key.

3. **`details` v3, then v4.** `StaffApplicationDetailsV3` added `consent.acknowledgedUnpaidVolunteer` and an optional `workSamples` text field ("Other links"), and kept `linkedin` (optional). v3 shipped to production data only if the first round was deployed, so it stays a union member. **v4** is v3 plus `gameDirector`, a free-text answer (see 8). v4 had not reached production when `gameDirector` changed from a fixed choice to free text, so v4 was redefined in place rather than bumped. New submissions write v4. `parseStaffApplicationDetails(raw, role)` is the server gate: it rebuilds a fresh v4 object from known keys, requires all three consents `=== true`, validates the LinkedIn URL with `normalizeLinkedInUrl` (blank allowed; a missing scheme gets `https://`; http/https only; the host must be `linkedin.com` or end in `.linkedin.com`, so `www.` and regional hosts such as `uk.linkedin.com` pass and look-alikes such as `linkedin.com.evil.example` or `user@host` tricks fail), caps `workSamples` at 1000 characters, requires the why-join answer, and requires (trimmed, non-empty, at most 500 characters) or clears `gameDirector` based on `role`. Admin and CSV labels for v3/v4: "LinkedIn", "Other Links", "Unpaid Volunteer Role", "Why EZ Esports", plus "Game Director Interest" first on v4 rows that have one, as plain text. **v1/v2 rows keep "LinkedIn / Portfolio"**, because those applicants answered a question that invited portfolio and resume links.

4. **CSV.** Staff CSV gains a "Resume" column ("Attached" or blank). No link is exported, because a signed link would expire within a minute.

5. **Migration `0036_staff_application_resume.sql`.** Generated with `drizzle-kit generate` (column add), then extended by hand:
   - `prevent_application_mutation()` is re-created from `0035` with `resume_storage_key` added to the staff immutability check and to the privacy-erasure `redacted_columns` audit list.
   - `erase_staff_application_privacy()` is re-created with `"resume_storage_key" = NULL` on redact. This only drops the pointer: the PDF must be deleted from the `staff-resumes` bucket separately. Read the key before redacting.

6. **Form UI.**
   - Step 2 is "Role & Resume": the division radios (with the Game Regulations follow-up, see 8), then a resume picker built on RAC `FileTrigger` + RAC `Button` (44px target, `aria-labelledby`/`aria-describedby` wired to the hint, the live filename/size status, and the error). Client-side type and size checks use the same `checkResumeFile` as the server. Below it: a "LinkedIn profile" `type="url"` input with an inline error (`LINKEDIN_URL_ERROR`, shared with the server), then an optional "Other links" input.
   - Step 3's label is "Why do you want to join EZ Esports? (approx. 4-7 sentences)". Both "3-6 sentences" strings are now "4-7".
   - Step 4 has a third required checkbox, `UNPAID_VOLUNTEER_ACK_TEXT`, with the same pattern as the Terms and Privacy boxes. It counts toward the progress bar.
   - 4xx error messages from the server (bad PDF, rate limit) are shown to the applicant. 5xx errors fall back to the generic message.

7. **Page intro (careers skeleton, per uiux case study 1).** The `h1` is followed by the mission statement, rendered once from `SITE_CONFIG.description` (no duplicate string). A meta chip reads "Unpaid volunteer · Part-time", so the role is known to be unpaid before anyone starts the form. Two short paragraphs cover the founding year (2021), about 300 matches a year across dozens of NYCDOE schools, hundreds of volunteers, Twitch Partner (linked from `SOCIAL_LINKS`), collaborations with Roc Nation, Gen.G, and Factor, and the 5th year in 2026–27. A three-line checkmark list covers: terms agreed before joining; part-time and remote-friendly; and who the role suits. The page makes exactly two statements about pay: the "Unpaid volunteer" meta chip and the required unpaid-volunteer acknowledgement in Step 4. There is **no future-pay or compensation wording** (an earlier "paid roles may become possible" line was removed). A link to `/leadership` (which redirects to the latest year) replaces a hardcoded year. The division list is **not** repeated in the intro: Step 2's radio list (`STAFF_ROLES`) is the single source.

8. **Game Regulations Division with an open-answer follow-up.** `STAFF_ROLES` replaces "VALORANT Division", "League of Legends Division" and "Teamfight Tactics Division" with one `GAME_REGULATIONS_ROLE` ("Game Regulations Division"). `STAFF_ROLES` also gained "Systems Engineering Division" and "Data Science Division", placed next to "Software Engineering Division", which is kept. The list is now nine divisions in this order: Software Engineering, Systems Engineering, Data Science, Marketing, Operations, Development, Productions Crew, Legal, Game Regulations. It follows the product owner's list, not the Discord recruiting post word for word (the post's "Software engineering & data science" became two separate divisions). Choosing Game Regulations reveals a required textarea, "Which game director position are you interested in?", with the hint "Tell us which game(s) and any experience you have with them."
   - **Open answer, not a fixed list.** An earlier iteration on this branch used a single-choice radio group of three director seats. It was replaced before deploy so applicants can name several games and describe their experience in one place.
   - Validation is `checkGameDirectorAnswer` (shared by client and server): trimmed, non-empty, at most `GAME_DIRECTOR_MAX_LENGTH` (500) characters. The textarea also has `maxLength` 500 and a visible count.
   - The `role` column still holds "Game Regulations Division", so admin status filters and the role shown in the table are unchanged. The answer is `details.gameDirector` (v4), stored trimmed, `''` for every other division, and dropped server-side if a stray value is sent with another division. Admin and CSV render it as plain text (React text node; `buildCsv` escaping).
   - Switching the division away from Game Regulations clears both the typed answer and its field error on the client, so a hidden stale answer is never submitted or flagged.
   - Old rows whose `role` is "VALORANT Division" etc. still render verbatim (free-text column). `isStaffRole` now rejects those values for new submissions.
   - UI: RAC `TextField` + `Label` + `Text slot="description"` + the shared `Textarea` (RAC `TextArea`) + `FieldError` (`validationBehavior="aria"`, `isRequired`, `isInvalid`), rendered directly after the division list in DOM order and only while Game Regulations is selected.

9. **Privacy Policy (`app/(marketing)/privacy/page.tsx`).**
   - "Information We Collect" lists phone number, Discord username, and a "Staff application materials" item (uploaded resume PDF, LinkedIn and other links, role, availability, written answers). "How We Use" covers staff applications. "Last updated" is September 2026.
   - **Retention policy (chosen by the user).** "Data Retention" keeps the general "only as long as necessary" sentence and then applies it to staff applications: an application, including its resume, is kept while it is being considered. If we decide not to move forward with it, we delete it, including the resume. Applicants can also ask for deletion at any time (Section 9).
   - **"Security"** says uploaded documents are in private storage that only "authorized EZ Esports staff and administrators" can open, through links that expire shortly after they are created. This matches the code: the resume route is gated by `getStaffForAdminSection('/admin/applications')`, i.e. `MANAGE_APPLICATIONS`, with `ADMINISTRATOR` and owners passing every permission check. The policy does not claim that downloaded copies expire.
   - **Keeping the retention promise is manual today.** Declining (status "rejected") or deleting an application in `/admin/applications` only writes a status log or sets `deleted_at`. Neither removes the row or the PDF. Until the automation in [open-threads.md](open-threads.md) exists, staff must run the runbook below whenever they decline an application or receive a deletion request.

   **Runbook: delete a staff application and its resume.** The order matters: erasure deletes the row, and the row holds the only pointer to the PDF, so read the key first.
   1. **Read the key.** In the Supabase SQL editor: `select id, resume_storage_key from public.staff_applications where id = '<application-uuid>';` Note the key (`<uuid>.pdf`). It is null for applications submitted before resumes were collected; if so, skip step 2.
   2. **Delete the PDF.** Supabase dashboard, Storage, bucket `staff-resumes`, delete the object named by the key. (Or the Storage API with the service role: `storage.from('staff-resumes').remove(['<key>'])`.) Confirm it no longer appears in the bucket.
   3. **Erase the row.** In the SQL editor: `select public.erase_staff_application_privacy('<application-uuid>'::uuid, '<your name or email>', 'delete');` The signature is `erase_staff_application_privacy(p_application_id uuid, p_actor text, p_operation text)`, where `p_operation` is `'redact'` or `'delete'` (`0035`, re-created in `0036`). `'delete'` removes the application's `application_status_logs` rows and then the `staff_applications` row, and the trigger records a metadata-only `privacy_erasure_events` entry (`operation = 'delete'`, actor from `p_actor`). `'redact'` only blanks the PII columns (including `resume_storage_key`) and soft-deletes; it keeps the row, so it is not what the retention promise needs. EXECUTE is revoked from PUBLIC and granted to `service_role`. The SQL editor normally runs as `postgres`, which applied the migrations and so should own the function. If the call is refused with "permission denied", run it over a service-role connection instead.
   4. **Verify.** `select count(*) from public.staff_applications where id = '<application-uuid>';` returns 0, and the object is gone from `staff-resumes`.

   These run against production. Per `CLAUDE.md`, do them deliberately, one application at a time, never through a script that reads the repo `.env`.

10. **Character limits on long-form answers.** The two long-form answers are capped on both sides and show a visible counter; the character-limit sentence ("Up to N characters.", via `characterLimitNotice`) appears only on the why-join answer. The Game Regulations answer and "Other links" keep their caps but carry no notice (product-owner decision). Each limit is enforced by `maxLength` in the browser and by the same cap on the server:
    - Game Regulations answer (textarea): 500 (`GAME_DIRECTOR_MAX_LENGTH`), with a visible n/500 counter and no limit sentence in its hint.
    - "Why do you want to join EZ Esports?" (textarea): **1,500** (`WHY_JOIN_MAX_LENGTH`, new). The prompt asks for about 4-7 sentences (roughly 600-1,000 characters), so 500 would cut real answers short. The check is `checkWhyJoinAnswer` (trimmed, non-empty, at most 1,500), shared by client and server, with a visible n/1,500 counter and "Up to 1,500 characters." in its description (`message-hint`, wired with `aria-describedby`).
    - "Other links" (single-line input, not a textarea): 1,000 (`WORK_SAMPLES_MAX_LENGTH`), enforced by `maxLength` and the server; no counter and no limit sentence.
    - The visible counters are `aria-hidden`. The Game Regulations radio carries an `aria-describedby` note saying a follow-up question comes next. Client validation mirrors the server message.

## Rollout order (manual, production)

Done for the first round: the `staff-resumes` bucket (private, 5 MB, `application/pdf`) and migration `0036` are live in production (2026-09-26). The follow-up round (v4 details, Game Regulations, LinkedIn host rule, privacy copy) needs **no schema change**, since `gameDirector` lives in the `details` jsonb. Do not edit `0036` in place; any future schema change gets a new migration.

## Invariants & Boundaries

- Resumes live only in the private `staff-resumes` bucket and are read only through the permission-gated signed-URL route. Never make the bucket public, never store or render a long-lived URL, and never put resume links in CSV exports.
- `resume_storage_key` is a submission field: append-only like the others, and changeable only through authorized privacy erasure.
- Privacy erasure of a staff application must also delete `staff-resumes/<resume_storage_key>`. The SQL procedure cannot do this.
- The server re-validates everything the client checks. Client checks exist for UX only.
- New submissions for Game Regulations always carry a non-empty `details.gameDirector` of at most 500 characters; other divisions always store `''`.
- The LinkedIn field only stores `linkedin.com` / `*.linkedin.com` URLs. Other links belong in "Other links".
- Every long-form answer (Game Regulations, why-join, Other links) has a client- and server-enforced character limit. Short fields (name, phone, Discord) have none.
- The Privacy Policy's staff-application retention promise (delete on decline or on request) is kept by the manual runbook in item 9 until automated.
- The staff apply page states pay only as "unpaid" (meta chip and Step 4 acknowledgement) and never suggests future compensation.
- Non-goals: resume virus scanning, resumes for school applications, and any further reshuffling of the division list (the role column is free text, so old values such as "VALORANT Division" keep rendering verbatim and no migration is needed for list changes).
