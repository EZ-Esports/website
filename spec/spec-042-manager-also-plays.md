## Context & Motivation

A school manager who also plays had to onboard twice: once through the manager invite and again through a player invite. The manager wizard already runs the same five steps as the player wizard (Discord OAuth, Riot ID, demographics and rules, consent, content screen), so the only things missing were the question, the games, and a player submission.

## Design Decisions

- **One person, one `members` row.** Members are matched by `members.email` (`upsertMemberRecord`). The combined path runs that once, so the manager and player records hang off the same member. Verified against the code, not assumed: `processOnboardingSubmission` already allows a Discord account whose existing owner *is* the member being written (`discordOwner && discordOwner !== memberId` is the only rejection), and `upsertPlayerIdentities` updates the member's existing Discord/Riot rows instead of inserting. So no schema or identity change was needed, and the unique `(provider, provider_user_id)` index still rejects a Discord account linked to a different member (`discord_already_linked`).
- **Reuse in both directions.** An existing manager who later uses a player invite, and a player who later uses a manager invite, attach to the same member as long as the email matches. A different email with the same Discord account is still a different member and is still rejected; that was deliberately not loosened. Known edge, left alone: `upsertMemberRecord` overwrites `members.school_id`, so using an invite from a second school moves the member to it.
- **Wizard.** Step 1 (manager invites only) gets a "Will you also be playing?" group with one checkbox, **I also play in this league**, unchecked by default. Checking it reveals a "Which games do you play?" checkbox list (`InviteData.playableGames`, supplied by `validateInviteToken` for manager invites only, from the `games` table). Because it defaults to unchecked, a non-playing manager sees one extra unticked box and nothing else changes: same five steps, same validation. For a playing manager the Riot ID step uses the player wording. Step 1 validation requires at least one game when the box is checked.
- **Which games are offered.** `listOnboardingGames` returns only games that have at least one season (rosters, and so applications, only exist for those; osu! and Minecraft have none). The list is then narrowed by the invite's staff-seeded `managedGames` slugs through `filterGamesByManaged` (null or empty means all games). That is the same rule `getAuthorizedGameScopes` applies, traced in `manager-auth.ts`: a manager only sees and approves games covered by an affiliation, so offering any other game would strand their own application. The check runs both when the wizard is loaded (`playableGames`) and again on submit. Known gap: `getAuthorizedGameScopes` also requires the game to have a season named like the manager's chosen affiliation (`YYYY-YY`); that cannot be checked at onboarding without knowing which season staff will have created, so a game with no matching season will show nothing in the portal until staff create one (same as for any manager of that game).
- **Riot ID for non-Riot games.** The identity step is not game-aware today: a manager (and any player invite, whatever the game) is asked for a Riot ID, stored as the single `riot` identity, and tracker links fall back to Valorant for non-LoL slugs. A non-Riot game offered here (a game that has a season) therefore behaves exactly like a player invite for it. There is no Riot flag on `games`, so the offer is not narrowed further; this is tracked with #247.
- **Submission.** `PlayerOnboardingSubmission` gains `alsoPlays?` and `playGameIds?`. They are honoured only for a manager invite and only when `alsoPlays === true`; the ids are bounded by `sanitizeGameIds` (`app/lib/onboarding/play-games.ts`) and every id must be among the offered games (above), otherwise the rejection `play_games_required` is returned before anything is written (wizard returns to step 1, flags the games group and focuses it). The result carries `playerApplicationsCreated` / `playerApplicationsExisting` (absent for manager-only), and the success page says "already on file" instead of "submitted" when nothing new was filed.
- **What gets created.** In the same transaction as the member, identities, demographics, consent, `school_managers` row and manager invite acceptance, one `player_invites` row per chosen game is inserted with `status = 'submitted'`, `member_id` set, `invited_by_user_id` taken from the manager invite, a random unreachable `token_hash`, and `submission_draft = { source: 'manager_also_plays' }` (`ensurePlayerSubmission` in `app/lib/db/onboarding.ts`). It is exactly what a player's own wizard submission leaves behind. A member that already has a live (not rejected or expired) row for that school and game gets no second one.
- **Same review and roster rules as any student.** The row shows up in the manager's Approve / Reject queue and is approved through `reviewPlayerInvite`, which already enforces the manager's season scope (`assertManagerForSchoolGame` and season resolution by name, spec-026), the inactive-season view-only rule (spec-028), the season roster lock (spec-020; staff admins exempt), one tier per game (spec-034) and roster size caps. Nothing in the portal, `enrollPlayerToRoster`, `getSchoolPlayerPool`, roster move or staff roster editing excludes a member who is also a manager, so after approval they can be rostered and can manage rosters. There is no auto-approval: a manager cannot bypass the lock by ticking the box.
- **Drafts.** `sanitizeDraftData` keeps `alsoPlays` only as a boolean and `playGameIds` only as a bounded list of unique strings; `saveOnboardingDraft` removes both from player-invite drafts. `managedGames` and `isPrimaryContact` stay staff-owned (the existing merge). `password` is still never stored, so the spec-035/041 password re-entry rules are unchanged; the choice and games survive the Discord round trip through the draft, and the second-tab flow keeps them in memory. The wizard ignores draft game ids that are not in `playableGames`.
- **Discord.** Done once, through the unchanged OAuth flow; the identity still comes only from the signed cookie.
- **Success page.** A playing manager sees an extra line that their player application is in the review queue, or that one was already on file when nothing new was filed.
- **Controls.** The checkboxes are native inputs with the same classes as the sibling wizard steps (Demographics, Consent); the wizard has no shared checkbox component, so none was introduced.

## Invariants & Boundaries

- No schema change, no migration, no new table.
- Manager-only onboarding is unchanged on the server (absent or false `alsoPlays` writes nothing extra).
- A browser cannot create a player submission for an unknown game, on a player invite, or without checking the box.
- Out of scope: auto-enrolling the manager on a roster, matching members by Discord when the email differs, and moving a member back when a second school's invite is used.

## Verification

- Pipeline tests, `app/lib/onboarding/__tests__/milestone4-player-wizard.test.ts`, describe "manager who also plays (issue #296)" (17 tests): manager-only creates no player submission; `alsoPlays=false` ignores sent game ids; combined path creates one member, one `school_managers` row linked to it, one Discord identity, one Riot identity and one `submitted` `player_invites` row; empty/missing/unknown game ids give `play_games_required` with nothing written; a Discord account owned by a different member is still rejected; manager-then-player and player-then-manager reuse the same member with one Discord identity; no duplicate application when the member already has one; created/existing counts (and absent counts for manager-only); `alsoPlays` ignored on a player invite; with `managedGames: ['valorant']` only that game is offered, a game outside it (alone or mixed) is rejected with nothing written and a managed game is accepted; `playableGames` only on manager invites; draft shape check plus staff-owned keys and removal from player drafts. Each was checked to fail under a deliberate mutation (count check, server and offered-list `managedGames` filters, same-member Discord rule, duplicate guard, manager-only gate, player-draft stripping, staff-key merge, created counter).
- Component tests, `app/(marketing)/join/[schoolSlug]/[gameSlug]/__tests__/manager-also-plays.test.tsx` (8 tests): unchecked by default and no games asked; not offered on a player invite; at least one game required before leaving step 1; draft restore ignoring unoffered ids; draft save carries the choice; games group flagged (`aria-invalid`, `aria-describedby`) with focus moved to the first game; success message differs between "submitted" and "already on file"; `play_games_required` maps to step 1.
- Review, roster-lock and season-scope behaviour is not re-tested here: the new row is an ordinary `submitted` player invite approved through `reviewPlayerInvite`, which the existing suites cover (`milestone3-portal-actions.test.ts` section 9, `season-lock-local-db.test.ts`). The `listOnboardingGames` "has a season" SQL filter is not exercised (the test DB mock ignores `exists`).
- Not checked in a browser or against real Discord/Supabase.
