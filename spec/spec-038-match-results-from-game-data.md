# spec-038: Match Results From Game Data (HenrikDev)

- **Spec ID:** spec-038
- **Title:** Fetch best-of-3 results and per-player stats from submitted Valorant match IDs
- **Status:** Shipped in PR #297 (issue [#290](https://github.com/EZ-Esports/website/issues/290)); migration `0054` applied to production 28 Oct 2026 (after a scoped pg_dump backup). Not yet verified against a real Henrik response; `VALORANTAPI` must be set in Vercel
- **Date:** 2026-10-27
- **Scope:** `app/lib/match-results/` (port, adapter, schema, scoring), `app/lib/db/match-results.ts`, `app/lib/onboarding/match-result-actions.ts`, the portal `MatchesSection` / `MatchResultControls`, migration `0054_match_games_from_game_data.sql`.
- **Relationship to other work:** the interim path while the official-Riot work is on hold. [#248](https://github.com/EZ-Esports/website/issues/248) (Riot match ingestion) and [#247](https://github.com/EZ-Esports/website/issues/247) (Riot Sign-On) stay open and untouched; this is built behind a port so Riot's official API can replace it by writing one adapter.

## Context & Motivation

Results were typed by hand or reported in Discord ([#242](https://github.com/EZ-Esports/website/issues/242)). A manager now pastes the Valorant match IDs (or tracker.gg links) of a best-of-3 and the site fetches the real games, scores the series, checks the players against the two rosters and saves the result.

## Design Decisions

- **Data source.** `GET https://api.henrikdev.xyz/valorant/v4/match/{affinity}/{match_id}` (affinity `na`), key in the `Authorization` header from env var `VALORANTAPI`. Server-only: read in `match-results/server.ts`, passed to the adapter's constructor, never returned, logged or sent to the client. Unset key = adapter reports `misconfigured` and the UI says to ask an admin; manual result entry is unchanged and remains the fallback.
- **Port/adapter (same style as `GameIdentityPort`, spec-011).** `MatchDataPort.fetchMatch(id)` returns `{ ok, game }` or a typed failure (`not_found | rate_limited | unavailable | invalid_response | misconfigured`). `HenrikMatchAdapter` is the only file that knows the URL, header and status codes. The app only sees `NormalizedGame`.
- **Schema validation.** `henrik-schema.ts` parses the response with zod (promoted from a transitive to a direct dependency, `^4.6.7`). Only the fields we use are required; the rest (rounds, kills, economy, locations) is ignored. A drifting payload fails as `invalid_response` instead of producing bad numbers.
- **MVP is derived, not read.** The documented v4 response has no MVP field. We calculate, as tracker.gg presents them: **match MVP** = highest score on the winning team, **team MVP** = highest score on the losing team; ties break on kills and a full tie yields none. The UI says "calculated by EZ Esports". If a live response turns out to carry a real MVP field, swap the derivation inside `normalizeHenrikMatch` only.
- **ACS** is `score / rounds played` (rounded), computed at read time. K/D, headshot % likewise.
- **Input.** The manager portal collects one field per game (game 1 and 2 required, game 3 optional; see [spec-052](spec-052-three-match-link-fields.md)) and joins them with newlines into the same `input` string. `parseMatchReferences` accepts bare UUIDs or `https://tracker.gg/valorant/match/<uuid>` (host exactly `tracker.gg` / `www.tracker.gg`), splits on whitespace/commas, rejects repeats and counts outside 2 to 3 **before any API call** (both in the browser and again on the server).
- **Scoring (`series.ts`, pure).** Games are ordered by start time, not paste order. Per game: queue must be `custom`, game completed with a winner, and not ended early (a surrender or forfeit, where the declared winner did not win more rounds, is flagged by the normalizer and refused with its own message rather than failing as `invalid_response`). **Roster rule:** each side must have exactly 5 players (`PLAYERS_PER_SIDE`; a 1v1, 2v2 or 4v5 is refused with "The Red team has 3 players; a league game has 5 per side.") and ALL of them must be on one school's roster for this match (every enrolled player of that roster, starters and subs, coaches excluded; a roster holds up to 10 players (spec-048; 5 subs at most), so any 5 of them may play). The two sides must belong to different schools; sides may swap between games. A ringer (anyone on a side who is not on that school's roster) rejects the game with a message naming the non-roster Riot IDs; a side split across both schools, a side that is entirely on both rosters, and two sides from the same school are rejected too. There are no warnings: a game is either between the two rosters or refused. The series needs two wins for one school and no game after it was decided; a 1-1 split after two games asks for the deciding game.
- **Scheduled-start window.** A game whose `started_at` is more than 1 hour before the match's current `matches.scheduled_at` is refused ("It started at ..., more than 1 hour before this match's scheduled start (...)", both times in ET). `scheduled_at` is the effective time: an approved reschedule (spec-032) overwrites it, so no extra lookup is needed. **There is deliberately no upper bound** (late and overrunning starts are legitimate, and a manager cannot gain anything by back-dating), so only scrims or earlier matches are caught. Exactly one hour early is accepted.
- **Throttle on fresh submissions.** At most one fresh submission per match every 30 seconds and ten per user per hour (`throttle.ts`, pure decision). Every fresh submission is recorded in `match_result_attempts` (persisted, so it holds across serverless instances); `reserveSubmissionAttempt` takes transaction advisory locks on the match and the user and checks-and-inserts atomically, with timestamps taken from the app clock so the database timezone cannot skew it. A "Check again" on saved IDs costs the same API calls, so it goes through the same check and is counted too (on top of the service's own `retry_after`, which is still honoured), which bounds repeated clicks. Staff admins submitting for a school are throttled exactly like managers (the limit is per user id, with no exemption). The error tells the user how long to wait. Attempt rows older than the one-hour window can no longer affect either limit and are deleted opportunistically inside `reserveSubmissionAttempt`; no cleanup job is needed.
- **Roster identity.** A roster's Riot IDs are `players.ign` plus verified `player_identities` rows with provider `riot`, lower-cased, coaches excluded. PUUIDs are not stored on our side (spec-011 note), so matching is by `Name#Tag` normalized with NFKC, whitespace collapsed, spaces around `#` removed and lower-cased (`normalizeRiotId`); a renamed account will fail validation until the roster is updated.
- **Never request a game twice.** Finished games are cached in `valorant_games` (+ `valorant_game_players`), keyed by the unique `riot_match_id`. `resolveSeries` reads the cache first and fetches only missing ids. A fetched game is stored once it passes the per-game checks (custom, completed, not ended early, placed between the two schools) and before the series is scored, so a series refused for its score (a 1-1 split) never costs a second request. A game that fails those checks is **not** stored (no strangers' data is persisted for rejected games), so resubmitting it requests it again. A game can be attached to only one league match (`match_games.game_id` unique, plus an up-front check) which is the duplicate rule; resubmitting to the same match is allowed.
- **Rate limit / outage.** `429` honours `Retry-After` / `X-RateLimit-Reset` (default 60 s, cap 1 h); 5xx and network errors count as unavailable. Only 5xx, 408 and network errors count as unavailable; any other 4xx (a malformed id) is a refused request, not an outage, and is never parked as pending. Rate-limit or outage saves a `match_result_submissions` row (`pending`, the ids, `retry_after`, message; one open per match via a partial unique index) and the portal shows "Waiting on the match data service" (a polite live region, with how many of the submitted games are already stored) with **Check again** and **Discard** (Discard asks through the in-app confirm dialog; buttons use `aria-disabled`). Retry is a user click only (no polling) and refuses to call before `retry_after`.
- **Pending rows are closed only when they can never succeed.** `resolveSeries` marks an invalid outcome `definitive` when every error is a rejection that re-asking cannot change: a roster, player-count, start-time, ended-early or not-custom refusal, a match that does not exist (404), or a game already counted for another match. A refused "Check again" with a definitive outcome cancels the pending submission so no stuck "waiting" row remains; the errors are shown and the manager pastes corrected IDs. If any error is not definitive (`misconfigured`: a missing or rotated key, 401/403; `invalid_response`: schema drift or another 4xx), the row is kept and the manager never has to re-paste IDs once the key or schema is fixed. A still-busy service (429/outage) keeps the row too. Separately, when the save finds the match can no longer take a result (completed or cancelled meanwhile, for example staff entered one) or the unique game index fires, the pending row is cancelled on both a fresh submit and a retry.
- **Saving.** `saveSeriesResult` runs in one transaction under a row lock: replaces `match_games`, writes `matches.home_score` / `away_score` (maps won) and `status = completed` (the columns manual reporting writes, so standings need nothing new), and closes the pending row. Under the row lock it refuses again if the match became completed or scored since the action looked (a racing submission or staff entry), returning false ("can no longer take a result"). A unique violation (23505, also read through drizzle's wrapped `.cause` chain) on a game's id is reported as "already counted for another match"; the pending-row insert recovers from the same race by refreshing the existing row. The action then calls `updateTag('matches' | 'rosters' | 'teams')` like the staff score action.
- **Who and when.** A manager of either school (for the match's game, in the match's own season; an inactive season is view-only) or a staff admin acting for one of the two schools. Only Valorant, only a match that has no result yet (`completed`/scored, cancelled and forfeit are refused; staff change those by hand).
- **PII.** The raw Henrik payload is **not** stored. Kept: map, times, rounds, and per-player name/tag/puuid/agent/tier and stat lines (the rostered students' public Riot IDs, which already live on rosters; opponents' stand-ins appear only if they played). Tables have RLS on with no policies (service role only).
- **Scoreboard.** Past-tab Result cell: **Scoreboard** opens a dialog with the series score and per-game tabs, two team tables (agent, ACS, K/D/A, K/D, HS%, damage, MVP badges). It is visible to the two schools' managers even while the season's outcomes are unpublished (spec-022 redaction still applies to the list's score column): they played and submitted these games. It is not on any public page.

## Invariants & Boundaries

- The key never leaves the server and is never in a message, log, test fixture or `.env.example` value (placeholder only).
- No test or CI path calls the live API: adapter tests inject a fake `fetch`, orchestration tests inject fake port/repository, action tests mock both.
- Do not call `fetchMatch` outside `resolveSeries` / the actions; every fetch must go through the cache.
- Games and the match's `home_score` / `away_score` must change together (one transaction); do not write scores for a fetched series elsewhere.

## Migration

`db/migrations/0054_match_games_from_game_data.sql` (hand-written like 0053, journal idx 54, no drizzle snapshot because snapshots stop at 0042): creates `valorant_games`, `valorant_game_players`, `match_games`, `match_result_attempts`, `match_result_submissions`, indexes, checks, RLS. Additive and `IF NOT EXISTS`; constraint names are under 63 characters. **Not applied to any database by this PR.** The owner applies it with `npm run db:migrate` (named host, fresh backup, per `CLAUDE.md`). Until applied, `getSchoolMatches` fails soft (the two new lookups log and return empty) and only the submit action would error.

## Verification

- Vitest with fixtures only: reference parsing, schema/normalization/MVP, adapter status mapping and key hygiene, series scoring (2-0, 2-1, 1-1, extra game, non-custom, strangers, same roster, stand-in, case, side swap, paste order), orchestration (cache hit, duplicates, 429/outage pending, store-before-validate), the server actions (input rejected before DB/API, authorization, refusals, success tags, pending save, retry wait) and the portal list wiring.
- Real Postgres (run locally, never against `.env`): `app/lib/db/__tests__/match-results.integration.test.ts`, skipped unless `TEST_DATABASE_URL` is a loopback URL. It applies all 55 migrations (including 0054) from an empty database, fires two concurrent `saveSeriesResult` calls for one match (exactly one wins; games and scores consistent), the same game submitted to two matches at once (the unique index admits one, the loser rolls back completely), a later save for a completed match, and the persisted throttle including six concurrent fresh submissions (exactly one passes). Removing the in-lock re-check makes two of these fail, so they do prove it.
- Not verified: a real Henrik response (the schema follows the published docs; the live key was not used), the SQL against a real Postgres (no local database was used), the migration, and a browser check of the dialogs at desktop and phone width.
