# spec-025 — League Setup season tabs and Matches deep links

**Status:** Implemented on branch `feat/schools-roster-view` (not pushed, no PR yet). **Date:** 22 Oct 2026. **Scope:** `app/lib/admin-season-filters.ts` (pure helpers), `app/(admin)/admin/league/page.tsx` + `LeagueSetupClient.tsx`, `app/(admin)/admin/matches/page.tsx`, `app/components/admin/AdminMatchExplorer.tsx`. No migration, no permission changes.

## Context & Motivation

League Setup listed every season ever created in one stack, so the few current ones were buried among archived seasons. Staff also had no way to jump from a season to its fixtures.

## Design Decisions

- **Season tabs (League Setup).** `Active | Inactive | All` with counts, via `AdminFilterTabs` (URL-driven Links, `segmentedItem`). The selection lives in `?status=active|inactive|all`; the server page validates it (`parseSeasonStatus`, unknown -> Active) and passes it down, so reload and shared links work. Active carries no param. Counts always reflect all seasons. An empty tab shows the shared empty state. All per-season actions (lock, publish/hide, edit, delete) are unchanged and work on every tab. A season created or deactivated while on a tab it no longer matches disappears from that tab (switch tab to see it).
- **View matches link.** Every season row has an always-visible "View matches" chip-link to `/admin/matches?season=<seasonId>&game=<gameSlug>` (`seasonMatchesHref`).
- **Matches & Standings filters.** The explorer already filtered by game, season, division, status and search (server-driven via `fetchStaffMatchesPage`). New: game and season are read from `?game=<slug>&season=<id>` on the server (`parseMatchFilterParams`) so the first page is loaded already filtered, and kept in the address (see "URL-driven filters"). Division, status, search and sort stay local state. Selecting a game already limited the season options.
- **Validation.** Unknown slugs, non-UUIDs and unknown ids are ignored. A season alone selects its game; a season that conflicts with the game wins. A game with no season param defaults to that game's active season when it has one; the explorer writes `season=all` when staff pick a game with "All seasons", so that choice survives reload. Plain `/admin/matches` is unchanged (all games, all seasons); the active-season default only applies once a game is chosen via the URL.
- **Invariants kept.** Both pages still authorize first (`getStaffForAdminSection`). Staff reads still use the raw `getMatchesPage` (spec-022); the filters only add `gameId` / `seasonId` params. Standings Archive untouched.

## Review follow-ups (22 Oct)

- **Season picked without a game.** The Season change (via `nextFiltersOnSeasonChange`, now inside `nextMatchFilterSearch`): picking a season also sets its game, so the Game select, season option labels and the written URL agree immediately and match what a reload would show (`parseMatchFilterParams`: a season alone selects its game). "All seasons" keeps the current game (`season=all` behaviour unchanged).
- **Same-route navigation (superseded).** The earlier key-remount plus `lastOwnSearch` echo-detection mechanism was removed; see "URL-driven filters" below.
- **Season moved tabs.** After a create or an edit (the Active toggle; there is no separate row activate button), `seasonMovedHint` compares the saved `isActive` with the current tab. If the season no longer matches, the success toast appends "It is now under the Inactive/Active tab." with a visible "Show Inactive/Active" link (`AdminToast` gained an optional `action`). The toast lasts 9 s instead of 3.5 s when it carries a link. Nothing is hover-gated.

## Back arrow on Matches & Standings (follow-up)

The "View matches" link on a League Setup season row now carries `from=league`. `matchesBackLink` (`app/lib/admin-season-filters.ts`) turns that into the page header's back arrow ("League Setup"), pointing at the tab the season lives on (`/admin/league?status=inactive` for an inactive season, since its row is not on the default Active tab). Only the known value `league` counts; anything else shows no arrow, as does a plain sidebar visit to Matches & Standings. The explorer's URL write keeps `from`, so the arrow survives a reload. Pages nested below a section (news editors, a school's rosters) already render the header's `back` arrow. Not verified in a browser.

## URL-driven filters (rewrite, 22 Oct)

The address is the single source of truth for Matches & Standings' game and season. `AdminMatchExplorer` holds no game/season state: it derives `{gameId, seasonId}` from `useSearchParams()` through `parseMatchFilterParams` (unknown slugs/ids, non-UUIDs fall back safely; `season=all` means all seasons for the game). Division, status, search and sort stay local `useState`.

- **Writing.** The Game/Season selects call `nextMatchFilterSearch(window.location.search, change, games, seasons)` (pure, in `app/lib/admin-season-filters.ts`) and then `window.history.replaceState` (per Next's docs this syncs `useSearchParams`/`usePathname` without a navigation, so the server page is not re-run). It parses the live location (not the rendered params), applies the change (game change drops a season of another game, "All games" clears the season, a season selects its game, "All seasons" keeps the game and writes `season=all`) and rewrites only `game`/`season`, preserving every other param, notably `from=league`, so the League Setup back arrow (rendered server-side from `from`) survives a reload. The arrow is computed on the server from the season in the URL at page load, so after a Season select change it can still point at the original season's tab until the next reload or link navigation (accepted). Because each change builds on the current location, rapid successive changes end on the last choice.
- **Reading / links.** Any link to the route (sidebar, "View matches") changes the search params, which changes the derived filters on the next render, so the shown filters always equal the URL. There is no local copy to race, so the old `lastOwnSearch` ref, echo detection (`filtersFromExternalNavigation`, `normalizeSearch`), the replaceState write effect and the page's `key={matchExplorerKey(...)}` remount were removed, as were the `initialGameId`/`initialSeasonId` props.
- **Fetching.** `initialPage` plus `initialFilters` (the validated game/season it was loaded for) come from the server. The explorer keeps `loaded` (the facets the shown rows belong to) next to the requested facets (URL game/season + local division/status/search/sort); one effect refetches page 1 whenever they differ. Only a pure search-text change is debounced (300 ms, `matchFetchDelayMs`); game/season/division/status/sort changes fetch at once. While requested != loaded, "Loading..." shows immediately, rows of another game/season are replaced by a skeleton (so old rows are never shown as the new filter's) and same-scope rows are dimmed; Load more is disabled. A sequence ref (bumped on every effect run) discards responses from superseded requests, and `loadMore` checks the same ref, so a Load more in flight when filters change cannot append old-filter rows. A failed refetch (22 Oct follow-up) leaves the rows, cursor and `loaded` facets untouched: requested != loaded keeps the stale (dimmed) state, an error toast shows, and an inline alert with a Retry button (bumps a tick that re-runs the fetch effect for the current facets) replaces the endless "Loading..." spinner. If the failed request was for another game/season the old rows stay hidden and only the alert shows. The failure is keyed to the requested facets, so changing any filter clears it. A failed Load more leaves the list intact with a toast; its button stays enabled as the retry. The disabled Load-more button is not rendered while the scope is stale.
- **Link navigation.** A link to the route re-renders the server page with a new `initialPage`. During render the explorer notices the new prop and, when its `initialFilters` differ from the `loaded` game/season (`shouldAdoptServerPage`), adopts the page (items, cursor) at once and resets division/status/search/sort to defaults, as the removed remount did: no stale rows, no redundant client fetch. Select changes use `replaceState`, so the server page does not re-render and they take the fetch path above. A server refresh for filters already shown (e.g. after a revalidation) is ignored, keeping local facets and loaded pages. Race fix: the explorer remembers the game/season its own select writes put in the URL (`ownWrite`, cleared when that fetch succeeds or a page is adopted); `shouldAdoptServerPage(server, shown, ownWrite)` refuses to adopt a server page for exactly those filters, so a refresh landing while a select-change fetch is pending no longer resets division/status/search/sort. Residual caveat: a link navigation to the very same filters as a pending own select change is also not adopted (the pending fetch loads the same scope; local facets are kept).
- **Behaviour change.** "All games" now also clears the season (before, a stale season could linger and re-select its game on reload).
- **Untested.** No component-test tooling (no jsdom/testing-library), so the explorer's hooks and the Next `replaceState` -> `useSearchParams` sync are not covered by a DOM test or a browser run; the pure URL builder/parser (`nextMatchFilterSearch`, `parseMatchFilterParams`, including rapid-change and round-trip cases) and the helpers `matchFacetsKey`, `matchFetchDelayMs`, `shouldAdoptServerPage` (including the `ownWrite` case) are covered in `admin-season-ux.test.tsx`. The render-time adoption, the sequence-ref discards (including Load more), the error/Retry flow and the skeleton/dim states are untested.
